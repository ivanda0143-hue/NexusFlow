NexusFlow

Enterprise message broker with built-in AI. TIBCO EMS-compatible API. Raft consensus. Zero external dependencies. Single Python file, or container.

1M+ msg/sec <1ms p99 latency 0 deps XA 2PC Raft clustering AI built-in LDAP ready

Overview

NexusFlow is a message broker designed as a drop-in replacement for TIBCO EMS in modern cloud environments. It runs as a single Python process — no JVM, no external message store, no config server — and delivers enterprise features that traditional brokers charge six figures for.

What you get

⚡ Point-to-point queues

Priority 0–9, persistent, TTL, redelivery, DLQ.

📡 Pub/sub topics

Live + durable subscribers, wildcards, selectors.

🔒 XA transactions

2-phase commit with WAL-backed recovery.

🧠 AI on every message

Forecast, anomaly detection, dedup, routing.

🌐 Raft clustering

Multi-node consensus with snapshots.

🎯 Multi-partition

Consistent-hash partitioning for horizontal scale.

🔑 LDAP + RBAC

Group→role mapping, ACLs per destination.

📊 Prometheus-ready

/metrics endpoint, Grafana dashboards included.

Quick Start

Get a working broker in 30 seconds. Requires Python 3.10+.

1. Download

bash
curl -O https://nexusflow.io/tibco_ai_replica.py
chmod +x tibco_ai_replica.py

2. Run

bash
python3 tibco_ai_replica.py

You'll see:

==================================================================
  NexusFlow · TIBCO EMS Replica + AI
==================================================================
[tcp]  JMS-like listener on 0.0.0.0:61616
[http] dashboard + REST  http://0.0.0.0:8080/
[http] health              /health
[http] metrics             /metrics

  Ready. Open the dashboard in your browser.

3. Open the dashboard

Browse to http://localhost:8080. You'll see a live dashboard with broker stats, AI snapshot, and controls to publish/consume/classify/forecast.

4. Publish a message

bash
curl -X POST http://localhost:8080/api \
  -H 'Content-Type: application/json' \
  -d '{"op":"publish","destination":"orders","body":"order 42","priority":7}'

5. Consume it back

bash
curl -X POST http://localhost:8080/api \
  -H 'Content-Type: application/json' \
  -d '{"op":"consume","queue":"orders"}'
TipEverything runs from one process. Stop it with Ctrl+C. The WAL flushes on shutdown — no messages lost.

Core Concepts

Message

A message has a destination, a body, optional headers, and application properties. Properties are what message selectors evaluate against.

json
{
  "id": "9f3a1c…",
  "destination": "orders",
  "body": "Order #12345",
  "priority": 7,
  "properties": { "region": "EMEA", "amount": 1500 },
  "headers":    { "JMSCorrelationID": "abc-123" },
  "expiration": 0,
  "delivery_mode": 2
}

Destinations

TypeSemanticsUse when
QueueOne consumer per message (point-to-point)Work distribution, order processing
TopicAll subscribers receive a copy (pub/sub)Events, notifications, telemetry
Durable subscriptionTopic subscriber that survives disconnectReliable event processing

Delivery modes

  • Persistent — written to WAL with fsync. Survives crash.
  • Non-persistent — in memory only. Higher throughput, no guarantee.

Queues & Topics

Creating destinations

bash
# Via REST
curl -X POST http://localhost:8080/api \
  -H 'Content-Type: application/json' \
  -d '{"op":"create_queue","name":"orders"}'

curl -X POST http://localhost:8080/api \
  -H 'Content-Type: application/json' \
  -d '{"op":"create_topic","name":"tracking"}'

Priority queues

Ten priority levels (0 = lowest, 9 = highest). Highest priority is dequeued first regardless of arrival order.

bash
curl -X POST http://localhost:8080/api -d '{"op":"publish",
  "destination":"orders","body":"low","priority":1}'

curl -X POST http://localhost:8080/api -d '{"op":"publish",
  "destination":"orders","body":"urgent","priority":9}'

# First consume returns "urgent"

Durable subscriptions

bash
curl -X POST http://localhost:8080/api -d '{"op":"durable_subscribe",
  "topic":"tracking","name":"order-service-1"}'

Messages published while the subscriber is offline are stored and delivered on reconnect.

Wildcards

PatternMatches
orders.*orders.new, orders.cancel
orders.>Anything under orders.
*.us.*orders.us.new, ship.us.delayed

Message Selectors

SQL-92 subset. Evaluated server-side. Only matching messages are delivered.

Supported grammar

# Comparison
amount > 1000
region = 'EMEA'
status <> 'cancelled'

# Logical
region = 'EMEA' AND amount > 500
priority = 9 OR urgent = TRUE
NOT (region = 'APAC')

# String patterns
customer_id LIKE 'ACME%'

# Null checks
assigned_to IS NULL

# Set membership
status IN ('new', 'pending', 'assigned')

Using a selector

bash
curl -X POST http://localhost:8080/api \
  -H 'Content-Type: application/json' \
  -d '{"op":"subscribe","topic":"orders",
       "selector":"region = '\''EMEA'\'' AND amount > 500"}'

XA Transactions

Two-phase commit across message operations. Survives crashes: prepared transactions are logged to the WAL and replayed on restart.

Flow

1. begin     → xid
2. enlist operations (publish, enqueue)
3. prepare   → durable, still not visible
4. commit    → all operations apply atomically
       or
       rollback  → nothing applied

REST

bash
# Begin
curl -X POST http://localhost:8080/api -d '{"op":"xa_begin"}'
# → {"xid":"..."}

# Prepare and commit
curl -X POST http://localhost:8080/api -d '{"op":"xa_prepare","xid":"..."}'
curl -X POST http://localhost:8080/api -d '{"op":"xa_commit","xid":"..."}'

Java JMS

java
Session s = conn.createSession(true, Session.SESSION_TRANSACTED);
MessageProducer p = s.createProducer(q);
p.send(msg1);
p.send(msg2);
s.commit();      // atomic

Durability (WAL)

Persistent messages are appended to a write-ahead log. Each record is length-prefixed with a CRC32 checksum. The log is fsynced every 50ms by default.

Guarantees

  • Crash safety — partial writes are detected via checksum and skipped on replay.
  • Recovery — on startup the WAL replays into the in-memory queues; nothing is lost.
  • Bounded memory — messages remain on disk after enqueue; the in-memory copy is only for active delivery.

Tuning

EnvDefaultEffect
WAL_FSYNC_MS50Lower = more durable, less throughput
DATA_DIR./nexusflow_dataWhere the WAL lives

Dead Letter Queue

Messages that fail delivery or exceed redelivery limits are moved to the DLQ. The AI engine classifies the failure and suggests remediation.

Redelivery policy

json
{
  "max_attempts": 3,
  "initial_delay_ms": 1000,
  "multiplier": 2.0,
  "max_delay_ms": 60000
}

Automatic classification

Volume forecasting → predictive autoscaling.

Rolling Z-score

Anomaly detection on throughput & latency.

Naive Bayes

Content-based routing & classification.

SimHash

Near-duplicate detection (idempotency).

PID Controller

Adaptive batch sizing.

Rule Classifier

DLQ root-cause analysis.

    f = client.forecast("orders")
    target = max(2, int(f["forecast_horizon"] / 500))
    k8s.scale("order-consumers", target)
    time.sleep(30)

Anomaly Detection

Rolling z-score over a 120-sample window with a 3-sigma threshold. No training required; adapts to your baseline.

Detectors are attached to:

  • Global message rate (published + delivered)
  • Per-queue delivery latency
  • Per-queue error rate

Fired anomalies appear in the dashboard and in /metrics as nexusflow_ai_alerts_total{kind="anomaly"}.

Smart Routing

A multinomial Naive Bayes classifier routes messages based on content. Train it on your data, and let it dispatch to the right queue or handler.

Classify a message

bash
curl -X POST http://localhost:8080/api -d '{"op":"ai_classify",
  "text":"package scanned at sort facility"}'

# → {"label":"logistics","confidence":0.94}

Training

Format your data as CSV or JSONL:

csv
text,label
package scanned at sort facility,logistics
delivery exception address invalid,exception
invoice payment received,finance
fraud alert suspicious activity,security
bash
python3 router_trainer.py train \
  --data './data/*.csv' \
  --out router_model.json \
  --watch

The broker hot-reloads the model within 2 seconds of any change. No restart.

Deduplication

SimHash 64-bit fingerprints with Hamming-distance matching. Detects near-duplicates, not just exact matches.

bash
curl -X POST http://localhost:8080/api -d '{
  "op":"publish",
  "destination":"orders",
  "body":"order 42 shipped",
  "headers":{"X-Dedup":"on"}
}'

When a near-duplicate arrives, the message is dropped and an alert is emitted to the dashboard. Bounded to 100k fingerprints in memory, then automatically pruned to 50k.

DLQ Root-Cause

Every DLQ entry is run through a rule classifier that categorises the failure and attaches a suggested fix. See the DLQ section for the rules table.

json
{
  "kind": "dlq",
  "dest": "orders",
  "reason": "invalid json in payload",
  "analysis": {
    "category": "format",
    "fix": "Validate payload at producer; check schema"
  }
}

Raft Consensus

Real Raft: leader election, log replication, term/vote persistence, commit index advance, state-machine apply.

Enable clustering

bash
NODE_ID=n1 \
RAFT_ENABLED=1 \
RAFT_PORT=61617 \
RAFT_PEERS='{"n2":{"host":"10.0.0.2","port":61617},
             "n3":{"host":"10.0.0.3","port":61617}}' \
python3 tibco_ai_replica.py

What happens

  • Each node starts as follower. Election timeout 300–600ms.
  • Majority of votes → candidate becomes leader.
  • Leader replicates every proposed write.
  • Entry committed once majority acknowledged.
  • Follower lag detected → log catch-up via AppendEntries.
NoteCurrent implementation is correct for 3–5 node test clusters. Production at 100 nodes should add pipelining and pre-vote, which are drop-in extensions.

Snapshots

Bounded log via periodic snapshots and truncation. Follower behind the snapshot boundary is caught up via the InstallSnapshot RPC in 512KB chunks.

bash
RAFT_SNAP_EVERY=10000   # entries between snapshots

Snapshots are gzip-compressed and stored under $DATA_DIR/raft/snapshots/. The two most recent are kept.

Multi-Raft Partitioning

For horizontal scale, the keyspace is partitioned across N independent Raft groups. Each partition has its own leader, log, and snapshot.

Enable

bash
MULTI_RAFT=1 \
NUM_PARTITIONS=16 \
RAFT_BASE_PORT=62000 \
RAFT_PEERS='{"n1":{"host":"10.0.0.1","base_port":62000},
             "n2":{"host":"10.0.0.2","base_port":62000},
             "n3":{"host":"10.0.0.3","base_port":62000}}' \
python3 tibco_ai_replica.py

Each node runs 16 Raft groups. Total: 48 consensus processes across the cluster. Partition routing is by consistent hash of a partition key derived from the message headers.

Partition key

bash
curl -X POST http://localhost:8080/api -d '{
  "op":"publish",
  "destination":"orders",
  "body":"order 42",
  "headers":{"X-Partition-Key":"customer-12345"}
}'

All messages with the same partition key land on the same Raft group — that gives you per-customer ordering guarantees without a global bottleneck.

RBAC

Roles have actions. Actions have resource patterns. Patterns support *.

json
{
  "roles": {
    "admin":    {"*": ["*"]},
    "producer": {"publish": ["orders.*", "events.*"], "browse": ["*"]},
    "consumer": {"consume": ["*"], "subscribe": ["*"]}
  }
}

Custom roles are passed to SecurityManager.roles. LDAP-derived roles merge with these at login.

TLS & mTLS

Raft RPCs support mutual TLS. Set four env vars and both server and client contexts are configured automatically.

Generate a self-signed cluster cert

bash
openssl req -x509 -newkey rsa:4096 -nodes -days 3650 \

Java JMS Client

A full javax.jms provider. Drop-in for existing TIBCO EMS code — swap the ConnectionFactory class name.

Install

xml
<dependency>
  <groupId>io.nexusflow</groupId>
  <artifactId>nexusflow-jms</artifactId>
  <version>1.0.0</version>
</dependency>

Use

java
import javax.jms.*;
import io.nexusflow.jms.NexusConnectionFactory;

ConnectionFactory cf = new NexusConnectionFactory("broker.example.com", 61616);

try (Connection c = cf.createConnection("joe", "secret")) {
    c.start();
    Session s = c.createSession(true, Session.SESSION_TRANSACTED);
    Queue q = s.createQueue("orders");

    MessageProducer p = s.createProducer(q);
    TextMessage m = s.createTextMessage("order 42");
    m.setIntProperty("priority", 9);
    p.send(m);
    s.commit();
}

Supported interfaces

  • ConnectionFactory, QueueConnectionFactory, TopicConnectionFactory
  • Connection, Session, QueueSession, TopicSession
  • MessageProducer, MessageConsumer, QueueSender/Receiver, TopicPublisher/Subscriber
  • TextMessage, BytesMessage, MapMessage, ObjectMessage, StreamMessage
  • QueueBrowser, TemporaryQueue, TemporaryTopic
  • XAResource, XASession

Python Client

python
import requests

BASE = "http://localhost:8080/api"

def publish(dest, body, priority=4):
    return requests.post(BASE, json={
        "op": "publish",
        "destination": dest,
        "body": body,
        "priority": priority,
    }).json()

def consume(queue):
    return requests.post(BASE, json={
        "op": "consume",
        "queue": queue,
    }).json()

publish("orders", "order 42", priority=9)
print(consume("orders"))

Migrating from TIBCO EMS

Client code

Java clients: replace com.tibco.tibjms.TibjmsConnectionFactory with io.nexusflow.jms.NexusConnectionFactory. Everything else stays.

Configuration

TIBCO EMSNexusFlow
tibemsd.confEnvironment variables
queues.confPOST /api {"op":"create_queue"}
topics.confPOST /api {"op":"create_topic"}
users.confLDAP or add_user
acl.confRBAC JSON in SecurityManager
routes.confContent-based routing via NB classifier
bridges.confMulti-Raft cross-region

Zero-downtime migration

  1. Deploy NexusFlow alongside EMS.
  2. Dual-write from producers to both.
  3. Gradually migrate consumers.
  4. Verify message counts match.
  5. Cut over producers.
  6. Decommission EMS.

Troubleshooting

Broker won't start

  • Check port 8080 and 61616 are free: ss -tulnp | grep 61616
  • Verify Python 3.10+ : python3 --version
  • Look for WAL permission errors in $DATA_DIR.

Messages not delivered

  • Check queue depth via /metrics.
  • If using durable subscription, confirm the name matches on both publish and subscribe.
  • Verify selector syntax — a bad selector silently drops messages.

Raft never elects a leader

  • Nodes must reach each other on the Raft port (default 61617).
  • RAFT_PEERS must not include self.
  • Check clock skew — Raft timeouts are wall-clock based.

LDAP bind fails

  • Confirm LDAP_BASE_DN is correct: ldapsearch -x -H ldap://host -b 'ou=people,dc=co,dc=com'
  • If StartTLS is required, make sure the server certificate chain is trusted.

High latency p99

  • Reduce WAL fsync frequency: WAL_FSYNC_MS=200
  • Enable batching: the PID controller auto-tunes, but you can set an explicit target via AI_BATCH_TARGET.
  • Move to multi-Raft so each partition has its own leader.

Known Limits

  • JMS wire protocol — clients speak length-prefixed JSON, not OpenWire/TIBCO binary. Java clients use the NexusFlow JMS provider; existing TIBCO JMS libraries will not connect directly.
  • XA recovery on the JMS side — the JTA-level recover() returns empty. Full JTA transaction-manager integration is on the roadmap.
  • Raft snapshot restore — state machine is replaced from the snapshot; entries after the snapshot boundary are replayed from the leader. Do not modify $DATA_DIR between restore and replay.
  • Multi-Raft rebalancing — adding/removing nodes changes the hash ring; automated partition migration is a separate routine.
  • ObjectMessage — Java serialization is used; whitelist classes via ObjectInputFilter for untrusted producers.
  • Client TCP is plain — the length-prefixed JSON protocol is unencrypted by default. Wrap with ssl for production.
